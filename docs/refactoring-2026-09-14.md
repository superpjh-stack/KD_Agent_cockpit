# 고객 업무 중심 리팩토링 · 2026-09-14

## 달라진 사용 흐름

기존에는 사용자가 지식베이스·DB·룰 중 어디에 질문할지를 먼저 판단해야 했다. 이제 ‘업무 시작’에서 프로젝트와 평가 기준일을 선택하면 확인 후보를 보고 담당 업무로 좁힐 수 있다. 각 항목에는 다음 조치, 판정 조건, 업무 원본, 룰 번호·개정·상태, 연결 문서가 함께 표시된다. ‘이 항목의 대응 절차 질문’을 누르면 식별자와 기준일을 포함한 질문이 기존 대화로 전달된다.

업무 시작 화면은 접어서 대화 공간을 확보할 수 있다. 추천 질문의 표시명을 ‘업무 절차·현재 현황·판단 기준’으로 바꾸고 문서 본문은 기본적으로 접었다. AI 사용 가능 여부도 실제 키 설정 상태에 맞춰 표시한다. API 키가 없어도 DB 조회와 확인 후보 평가는 동작한다. 자연어 답변과 음성은 API 연결이 필요하다.

## RAG·업무 DB·룰 DB의 분담

| 구분 | 맡길 내용 | 경동 예시 | 변경할 때의 기준 |
|---|---|---|---|
| RAG | 이유, 절차, 작업표준, 사례, 승인 흐름 | 대체자재 승인 절차, FAT 재시험 체크리스트 | 문서 소유자가 개정·유효일·승인 상태를 관리 |
| 업무 DB | 수량, 측정값, 상태, 날짜, 식별자 등 사실 | LOT 재고, 발주 예정일, 실제 작업시간, 검사 결과 | 원천 업무 시스템의 기록을 갱신 |
| 룰 DB | 반복 점검할 조건, 담당자, 조치, 근거 문서 | 예상 입고일이 약속일 이후이면 구매 담당자가 납기를 재확인 | 조건과 근거 개정을 함께 검토하고 평가 회귀 검증 |

예: ‘자재 부족은 어떻게 처리하나’는 RAG가 절차를 설명한다. ‘어느 LOT가 부족한가’는 DB가 사실을 제공한다. ‘누가 무엇을 확인해야 하나’는 룰과 해당 레코드를 연결한다. 문서 검색의 유사도는 합격·불합격 판정값으로 쓰지 않는다.

## 구현 변경

- `rules.py`: 회사명·프로젝트 번호에 의존하지 않는 읽기 전용 평가 모듈. 현재 저장된 7개 조건을 검토된 함수로 평가한다. SQL이나 Python 표현식을 DB에서 실행하지 않는다.
- `data_hub.py`: 프로젝트별 평가 조회와 입고검사→LOT→프로젝트 연결. 화면의 50건 페이지 제한과 별개로 전체 대상 레코드를 평가한다. 기존 스키마·데이터를 덮어쓰지 않는다.
- `factory_tools.py`: AI도 동일한 `evaluate_rules` 도구를 호출하도록 연결.
- `workbench.py`: 프로젝트·기준일·담당 업무 선택, 확인 후보, 원본과 문서, 대화 연결 UI를 분리.
- `service.py`와 `app.py`: DB·룰 도구의 요청 인자와 반환 결과를 메시지별 근거로 보관하고 펼쳐볼 수 있게 함. 기존 문서 검색 근거도 유지.
- `prompts.py`: 현황·조건·절차를 구분하고 미평가·샘플 상태를 밝히도록 지침 추가.

현재 평가기는 `(source_table, condition)`의 정확한 조합으로 지원 여부를 확인한다. DB에서 조건 문구를 바꾸면 기존 함수가 계속 실행되지 않고 ‘미평가’로 드러난다. 새 조건은 평가 함수와 경계값 테스트를 함께 등록해야 한다. 이는 범용 무코드 룰 편집기가 아니다.

평가 결과 0건은 정상이나 출하 승인을 의미하지 않는다. 필수 값 누락과 지원하지 않는 조건은 별도 미평가 목록에 표시한다. 확인 후보는 룰별·레코드별 건수이므로 한 작업에 여러 후보가 있을 수 있다. 샘플 룰·문서는 계속 검증용이며 승인·발주·출하를 실행하지 않는다.

## 다른 회사에 적용할 때

그대로 재사용할 부분은 ‘대상 선택→확인 후보→담당자·조치→근거→질문’ 흐름, 읽기 전용 평가와 미평가 처리, DB·룰·문서 근거 보관 방식이다. 회사별로 교체할 부분은 업무 테이블·식별자 연결, 승인된 문서, 룰 조건과 책임자, 브랜드·용어·추천 질문이다. 경동 고객·LOT·프로젝트 샘플을 타사 운영 데이터로 복사하면 안 된다.

적용 순서는 핵심 업무 한 가지 선정, 실제 원천 필드 연결, 승인된 문서 연결, 담당자와 조건 검토, 알려진 과거 사례로 재현 검증, 현업 사용자 확인이다. 우선 자재 부족·입고 지연·검사 보류처럼 원천 값과 다음 조치가 분명한 업무에 적용하는 것이 적합하다.

추가 제품화 시에는 조건 문구 대신 버전이 있는 구조화 조건(JSON AST 등)을 저장하고, 문서 개정·유효일·승인 상태를 별도 컬럼으로 관리할 수 있다. 테넌트별 데이터 접근 통제, 평가 이력 저장, 원천 데이터 갱신 시각, 운영 승인 프로세스도 별도 구현이 필요하다. 이번 작업은 여러 회사를 동시에 서비스하는 멀티테넌트 전환까지 포함하지 않는다.

## 검증과 남은 확인

자동 검증: 24개 통과, PostgreSQL 초기화 테스트 1개는 관리자 연결 URL 미설정으로 건너뜀. 프로젝트 범위와 검사 LOT 연결, 날짜 경계와 완료 작업 제외, 누락 값, 변경 조건의 미평가, 110개 추가 레코드의 평가 누락 방지, 잘못된 인자와 읽기 전용 동작을 확인했다. Streamlit AppTest로 첫 렌더, 프로젝트 변경, 새 대화 두 번, 테이블 변경, API 없는 업무 질문 동작을 확인했다.

실제 OpenAI 호출, PostgreSQL 서비스 및 컨테이너 기동, 데스크톱·모바일 브라우저의 시각 검수는 이번 검증에 포함하지 않았다. AI의 도구 선택은 프롬프트 지침과 모델 호출에 의존하며, 모든 자연어 질문에서 룰 평가가 강제되는 구조는 아니다. 배포 전 이 환경에서 통합 확인이 필요하다. 서버 배포는 수행하지 않았다.
