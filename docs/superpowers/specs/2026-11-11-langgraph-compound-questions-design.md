# 경동글로벌텍 LangGraph 복합질문 상세설계

작성일: 2026-11-11
상태: 설계 검토 요청 / 제품 코드 미적용

## 목적과 성공 기준

하나의 질문에 포함된 납기·자재·설계·품질·원가·절차 요청을 각각 처리하고 근거를 묶어 답한다. 텍스트와 실시간 음성이 동일한 분석기를 사용한다. 호출명은 요구하지 않는다. 현재 입력창 고정, 모바일 화면, 기존 질문 두 그룹은 유지한다.

성공 기준은 복합질문의 요청 항목별 답변 여부와 근거 연결이다. 여러 도구를 호출했다는 사실만으로 성공으로 간주하지 않는다. 확인 불가능한 항목은 미확인, 조회 실패는 실패로 구분한다. 샘플 문서와 가상 데이터라는 표시는 유지한다.

## 현재 구현과 문제

- `v2/api.py` 데모 조회는 if/elif로 도구 하나만 선택한다. 자재와 FAT를 함께 물으면 한 항목이 빠질 수 있다.
- `kyungdong_agent/service.py` AI 분석은 Responses 도구 루프와 근거 누적을 지원하지만 요청 항목별 완료 여부를 추적하지 않는다.
- 음성은 개별 제조 도구를 호출한다. 텍스트와 분석 흐름이 다르다.
- 기존 도구에는 프로젝트·설계·공정, 자재, 입고검사, 구매, FAT, 견적, 납기, 문서 검색과 규칙 평가가 있다. 이를 재사용한다.
- 현재 로컬 Python 가상환경은 3.9, Docker는 3.12이다. LangGraph 호환 버전을 확인하고 V2 전용 Python 3.12 환경을 구성한다. 기존 가상환경은 보존한다.

## 접근 방식 결정

1. 기존 도구 루프를 그래프로 감싸기: 변경은 작지만 요청 누락 점검이 부족하다.
2. 계획·조회·검증·종합을 명시한 StateGraph: 요청별 근거와 종료 조건을 관리할 수 있다. **채택한다.**
3. 역할별 자율 에이전트: 호출량과 응답시간이 늘고 현재 읽기 전용 도구 규모에서는 불필요하다.

LangGraph만 도입하며 LangChain 모델 래퍼와 외부 추적 서비스는 필수 의존성으로 추가하지 않는다. 기존 OpenAI 클라이언트와 모델 설정을 유지한다.

## 그래프 상태와 실행

흐름: START → normalize → plan → validate_plan → retrieve → assess → synthesize → END.
assess에서 근거가 부족하고 예산이 남으면 plan으로 돌아간다. 식별자가 모호하면 clarify로 이동해 한 가지 확인 질문으로 종료한다.

상태 필드:
- question, bounded_history, mode, request_id
- selected_project, explicit_project_ids, effective_scope
- tasks: id, user_request, tool, validated_arguments, dependency_ids, status
- results: task_id, tool, arguments, source, records, retrieved_at, error
- coverage: 요청 항목별 supported / empty / failed / needs_clarification
- evidence, missing_items, iteration, call_count, deadline
- answer, voice_summary, public_steps

실행 규칙:
- AI 모드의 planner는 구조화된 계획을 반환한다. 허용된 도구 이름, 인자 타입, 프로젝트 존재 여부를 서버에서 검증한다.
- 데모 모드는 다중 키워드·의도 규칙으로 여러 조회를 계획한다. 자유로운 의미 추론을 지원하는 것처럼 표시하지 않는다.
- 독립 조회는 최대 3개 동시 실행한다. 프로젝트 발견 후 해당 프로젝트를 조회하는 의존 작업은 순차 실행한다. 도구마다 별도 DB 연결을 사용한다.
- 동일 도구·동일 인자 조회를 한 요청 안에서 중복 실행하지 않는다.
- 최대 2회 계획, 총 12회 조회, 전체 90초를 상한으로 한다. 남은 시간보다 긴 모델 호출을 시작하지 않는다. 도구 오류는 결과로 수집하고 성공한 근거는 보존한다.
- 상태를 요청별로 생성한다. 영구 체크포인터와 사용자 간 공유 메모리는 초기 범위에서 제외한다.

## 범위와 근거 검증

질문에 명시된 프로젝트가 있으면 해당 프로젝트를 사용하고, 없으면 화면에서 선택한 프로젝트를 사용한다. 둘 다 없으면 전체 조회한다. 명시적으로 여러 프로젝트를 비교하는 경우에만 비교 범위를 확장한다. 후속 질문의 대상이 불명확하면 확인 질문을 한다.

`get_db_records`는 현재 프로젝트 인자를 받지 않으므로 별도 어댑터에서 범위를 필터링한다. 안전하게 프로젝트에 연결할 수 없는 레코드는 프로젝트별 근거로 쓰지 않는다. 명시적 비교를 제외하고 모델이 선택 범위를 임의로 확장하지 못하도록 validate_plan에서 제한한다.

문서 지침은 실제 작업 결과로 간주하지 않는다. 숫자·단위·ID는 원본에서 가져오고, 계산 결과에는 입력값과 계산식을 기록한다. 서로 다른 단위나 예상/실제 값을 합산하지 않는다. 공수만으로 잔여기간을 확정하지 않고, 사건 간 상관관계를 원인으로 단정하지 않는다.

답변은 핵심 결론, 요청별 결과, 다음 확인 사항, 근거로 구성한다. 근거 없는 항목을 채워 넣는 대신 미확인 사유를 적는다. 우선순위 제안은 저장 규칙 또는 명시한 판단 기준을 바탕으로 하며 제조 승인이나 자동 실행을 수행하지 않는다.

## API와 화면

`POST /api/chat`의 입력과 기존 응답 필드를 유지하고 내부에서 공통 그래프 서비스를 호출한다. 응답에 `analysis_steps`, `coverage`, `partial`, `voice_summary`를 추가한다. 기존 evidence와 data_evidence는 유지한다.

우측 제목은 ‘추천질문리스트’를 유지한다. 탭은 ‘데이터 대시보드’, ‘지식베이스’, ‘복합질문’으로 구성한다. 각각 10개이며 앞에 01–10 번호를 표시한다. 모든 표시 질문에서 ‘경동아,’를 생략한다. 클릭하면 현재 프로젝트 범위와 현재 모드로 전송한다.

복합질문 결과에는 실제 수행한 조회 단계와 부분 성공 여부를 보여준다. 모델 내부 추론은 표시하지 않는다. 처리 중에는 일반 진행 표시를 사용하며, 단계별 실시간 스트리밍을 구현하지 않고 진행률을 꾸미지 않는다. 모바일에서는 세 탭이 줄바꿈되거나 가로 스크롤되도록 하고 입력창 고정과 대화 영역 스크롤을 유지한다.

## 추천 복합질문 10개

| 번호 | 질문 | 주요 조회 |
|---|---|---|
| 01 | 납기 위험 프로젝트의 자재 부족과 발주 지연을 함께 확인하고 우선 확인할 일을 정리해줘. | 납기, 자재, 구매, 규칙 |
| 02 | 설계 변경 승인 대기와 진행 중인 공정을 비교하고 영향 확인에 필요한 자료를 알려줘. | 프로젝트·설계·공정, 도면변경 절차 |
| 03 | 입고검사 보류 자재의 MTC와 재고 상태를 확인하고 재검사 절차를 알려줘. | 입고검사, 자재, 입고검사 문서 |
| 04 | FAT 불합격 항목과 재시험 계획을 납기 현황과 함께 정리하고 출하 전 확인사항을 알려줘. | FAT, 납기, FAT 체크리스트 |
| 05 | 프로젝트별 예상 원가·이익률과 납기 위험을 비교하고 추가 검토 대상을 정리해줘. | 견적, 납기, 원가 지침 |
| 06 | 부족 자재의 발주 일정과 대체 공급사 후보를 확인하고 대체 승인 절차를 알려줘. | 자재, 구매, 대체승인 문서 |
| 07 | 공정별 계획·실제 공수를 비교하고 초과 공정의 품질 기록과 관련 작업표준을 찾아줘. | 공정, 납기, FAT, 작업표준 |
| 08 | 용접·조립 진행 상태와 설계 변경 이력을 확인하고 검사 전에 필요한 기록을 정리해줘. | 프로젝트·설계·공정, 용접검사 문서 |
| 09 | 납기 지연과 FAT 재시험이 함께 있는 프로젝트를 찾아 관련 기록과 대응 절차를 정리해줘. | 납기, FAT, 납기대응 문서 |
| 10 | 선택 범위의 자재·설계·품질·납기 이슈를 종합하고 담당자와 다음 확인사항을 정리해줘. | 프로젝트, 자재, FAT, 납기, 규칙 |

‘원인’, ‘영향’, ‘담당자’ 정보가 데이터에 없으면 추가 확인이 필요하다고 답한다. 선택 범위 안에 조건을 만족하는 대상이 없을 때 다른 프로젝트를 임의로 끌어오지 않는다.

## 음성 통합

Realtime의 업무 분석 도구로 `analyze_manufacturing_question`을 추가하고, 제조 질문은 이 도구를 통해 공통 그래프 서비스를 사용하게 한다. 서버에 선택 프로젝트와 제한된 대화 이력을 명시적으로 전달하고 검증한다. 도구 결과에는 짧은 음성 요약과 구조화된 상세 근거를 함께 반환한다.

브라우저는 상세 근거를 evidence/data_evidence 형태로 표시하고 Realtime은 2–3문장으로 요약한다. 문서 근거와 테이블 근거를 동일 화면에 표시한다. 인사 등 업무 조회가 필요 없는 발화는 직접 응답할 수 있다. 호출명은 요구하지 않는다.

새 질문, 음성 종료, 프로젝트 전환 시 이전 요청의 결과를 현재 대화에 섞지 않는다. 발화별 식별자와 세션 epoch로 지연 결과를 폐기하고 진행 중 fetch를 중단한다. 서버는 연결 종료 신호와 실행시간 상한을 확인한다. 외부 모델 호출이 이미 시작된 경우 완전한 과금 취소를 보장하지 않는다. 응답 생성은 직렬화해 중복 재생을 막는다.

## 변경 대상

- 신규 `kyungdong_agent/compound_graph.py`: 상태, 그래프, 계획 검증, 조회 예산, 근거 종합
- 신규 `kyungdong_agent/compound_questions.py`: 추천 복합질문과 데모 의도 매핑
- `v2/api.py`: 그래프 호출, workspace 질문 그룹, 음성 분석 도구
- `v2/web/src/App.tsx`, `hooks/useRealtimeVoice.ts`, `styles.css`: 질문 탭, 분석 결과, 음성 근거 변환과 요청 격리
- `v2/requirements.txt`, `v2/Dockerfile`, 실행 안내: Python 및 LangGraph 의존성 일치
- `v2/tests`: API·그래프·브라우저 회귀 및 음성 모의 테스트

기존 Streamlit 서비스와 공용 ManufacturingAgent를 일괄 교체하지 않는다. V2의 공통 분석 서비스부터 연결한다. 현재 변경 중인 화면·음성 파일은 덮어쓰지 않고 기존 수정 위에 적용한다.

## 검증 및 인수 기준

1. 추천 3개 그룹이 각각 10개이며 호출명 없이 선택·전송 가능하다.
2. 자재+FAT+문서 질문이 각 분야 근거를 반환한다. 요청 항목별 coverage가 실제 결과와 일치한다.
3. 질문에 없는 프로젝트의 기록이 섞이지 않는다. 명시적 다중 프로젝트 비교도 검증한다.
4. 빈 결과, 부분 도구 실패, 잘못된 계획, 호출 상한, 시간초과, 근거 없는 계산을 검증한다.
5. 데모는 키 없이 동작하며 AI 실패를 데모 성공으로 위장하지 않는다.
6. 모의 모델로 계획·검증·추가 조회 경로를 결정적으로 검증한다. 실제 모델 검증 결과는 별도로 기록한다.
7. 음성 모의 테스트로 분석 도구 호출, 상세 근거 표시, 중복 응답 방지, 전환 후 이전 답변 폐기를 검증한다.
8. PC 1440px와 모바일 390px에서 탭, 질문, 근거, 고정 입력창과 가로 넘침을 확인한다.
9. Python 테스트, 프런트엔드 빌드, 브라우저 검증을 통과한다. 실제 모바일 음성 검증 및 운영 배포 여부는 따로 명시한다.

## 설계 자체 검토

기존 정책(호출명 불필요), 20개 질문 보존, 별도 복합질문 10개 추가, 범위 검증, 부분 실패 처리, 음성 근거 변환, Python 환경 차이를 포함했다. 초기 범위에서 영구 대화 저장·외부 추적·설비 제어는 제외했다. 구현 전 이 설계의 검토가 필요하다.
